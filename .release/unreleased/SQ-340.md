---
ref: SQ-340
title: A board can be switched to PR delivery, from the board_config tool or the board-config CLI
bump: minor
plugins: [sidequest]
---

PR delivery has been implemented since US-3 and unreachable ever since. `deliveryChannelFor` in `submissions.ts` gates it on `deliveryChannel.mode === 'pr'`, `setBoardConfig` has always accepted and validated that patch, and `boardConfig` has always returned the resolved channel. Nothing wrote it: the `board_config` tool did not declare the property, so an MCP caller setting it was refused by name as an unknown argument, and no `board-config` flag existed in any shipped build. Every board therefore stayed on local delivery, and `integrate` advanced the integration branch in the operator's checkout no matter what the repository required.

That gap is what put a hand procedure in this repo's own delivery rule: integrate, then push a branch and open the pull request yourself. On the night this ticket was filed it cost three hand-built pull requests.

The switch is now exposed on both surfaces, writing through the same kernel validator rather than a second copy of it:

```
sidequest board-config --delivery-channel pr
sidequest board-config --delivery-channel pr --delivery-remote upstream --delivery-target release/next
sidequest board-config --delivery-channel none
```

`--delivery-remote` and `--delivery-target` need a mode in the same command, because a channel write replaces the whole record. Accepting a destination on its own would reset the mode to local while appearing to set where the work goes, which is the one failure that would look like PR delivery was configured. `--delivery-channel none` clears the channel, as `deliveryChannel: null` does on the tool.

`delivery` and `deliveryChannel` are two different settings and the old description invited reading them as one. "Default submission delivery mode" now says which it is: the git strategy `integrate` uses to apply a wave (`merge`, `replay`, `apply`). `deliveryChannel` says whether that lands locally or behind a pull request. The CLI prints them on separate lines, and the getting-started guide now documents PR delivery, which it never mentioned.
