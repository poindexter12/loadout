---
ref: SQ-319
title: "sidequest: refuse an empty verify command under kind command, and name the command a derived requirement or a mismatch is talking about"
bump: patch
plugins: [sidequest]
---

A ticket could be stored with `verifyKind: command` and no command at all. The command validator returned no error for an empty string and the kind classifier kept the declared kind, so `add` and `update` both accepted the pairing. Dispatch then found no command to pin and fell through to the ticket's named suite, which for a plugin ticket is that plugin's whole suite, and it did so silently: nothing in the dispatch result or in pulse said the requirement had been derived rather than taken from the ticket. The executor was handed a gate its ticket never asked for, and because the mismatch refusal named neither the captured command nor the expected one, a submission that failed to reproduce the pinned string byte for byte gave no clue which string it was missing. On SQ-300 that cost over three hours of full suite and two negative controls before the empty field was found by hand in the board database.

`add` and `update` now refuse an explicit `command` kind with an empty or whitespace-only command, naming the field the caller passed, at both the MCP surface and the store, so no path can write that state. An omitted kind still defaults to `command` and still files a ticket with no command, because filing before the verifier is known is ordinary. A requirement that genuinely has to be derived, which is now only the case of a ticket that records no verify of its own, carries a `verificationDerivation` record naming the derived kind, command and suite: the dispatch result warns in words, the pulse `dispatch` block exposes the record, and pulse `warnings` repeats it so the notice survives into the compact read that orchestrators actually see. Re-pinning a real command clears the notice rather than leaving it describing a superseded gate. The `executor_verify_mismatch` refusal now prints the command the submission had to match, JSON quoted so padding and nested quotes stay visible in a string an executor has to reproduce byte for byte.

One detail of the original report turned out not to match the code. The ticket held that submit refused because the stored command was empty; an empty command cannot produce that refusal, because the comparison runs only when a command exists and takes the expected value from it. An empty pinned command instead makes submit accept whatever evidence it is given. The refusal on SQ-300 came from the silently derived suite command, which the executor's captured string did not reproduce. The empty case is kept in the refusal as a guard with a comment saying so, and is deliberately untested, since nothing can reach it; the accept-anything path behind it is noted on the ticket as worth its own fix if the guards above it are ever loosened.
