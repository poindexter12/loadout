---
ref: SQ-260
title: The home-delete guard scans an ssh payload as a remote shell command, against a remote protected set
bump: patch
plugins: [sidequest]
---

`ssh host 'rm -rf ~'` was allowed. The home-delete guard finds a delete by scanning the command string for a delete verb at a command position, and a quote is exactly what stops that scan from reaching inside an ssh payload: the opening `'` is neither a command separator nor part of a word, so no verb was ever found. Everything a remote shell would run was invisible to the guard, including `rm -rf ~/.claude` and `rm -rf /home/<user>`. Only the unquoted spellings were caught, by accident, and they were reported as a local wipe.

An ssh invocation's payload is now extracted and scanned as its own command. The tokenizer already strips the quotes that hid it, so the words after the destination (skipping ssh's own options, including the ones that take a separate argument) are rejoined and run back through the same delete matching, one hop deep for a nested `ssh a 'ssh b "rm -rf ~"'`.

What a remote payload is measured against is deliberately not the local set. A remote `~` is the remote user's home, not this machine's, so it cannot be expanded here; it stands in as an unresolved home component instead. The remote set is the remote filesystem root, the conventional home roots `/home` and `/Users`, any one-component home under them, the root account's home, and the `.claude` root inside any of those. A payload deleting an ordinary subdirectory stays allowed, recursively or not, so the false positives fixed in the previous guard rewrite do not come back through the remote path.

A remote wipe and a local one are not the same event, so they do not share a refusal. The remote one names the matched target: `blocked a recursive delete of remote profile root (matched "~")`.
