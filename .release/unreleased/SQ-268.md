title: Preparing a dispatch no longer holds the board write lock across its Git and filesystem work
bump: patch
plugins: [sidequest]
commit: 2c4efa7ade2c1676ec931a4383acda9eb7612452
---

Every project shares one board database and SQLite takes one writer at a time, so `dispatch` was the board's hottest lock-holding path: it held the write lock across its Git subprocesses, across a recursive read of the entire project on filesystem-snapshot projects, and across the two synchronous filesystem writes that create a dispatch's token and evidence directory. On this board that measured 2367ms of a 2650ms dispatch, during which a hook in an unrelated project could only wait. Preparing a dispatch now does all of that work before taking the lock, and takes the lock only to check cheaply that nothing moved and then store. The check compares a hash of the stored rows the plan actually read, which are its ticket, its review target, its story and its project, against those same rows as they stand under the lock, plus a stamp of the repository's ref state read from files rather than from Git. If either moved the dispatch is planned again, up to three times, and then refuses having written nothing rather than storing a plan that describes a board or a checkout that no longer exists. What the lock still covers is unchanged: a dispatch's state, its baselines and its token commit together, so there is still no moment where a token file can be read before the dispatch row that authorizes it exists. The same hold now measures 38.5ms, taken at a machine load where a single Git subprocess costs 219ms.
