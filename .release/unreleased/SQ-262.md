---
ref: SQ-262
title: Board write-lock contention can be measured with an opt-in lock trace
bump: minor
plugins: [sidequest]
---

Every project shares one board database, and SQLite takes one writer at a time, so a slow write in one project makes another project's hooks wait on it. There was no way to tell how much of that was actually happening. Setting `SIDEQUEST_LOCK_TRACE=1` now appends one JSON line per board write to `lock-trace.jsonl` beside the board database (or to a path given as the variable's value), recording how long the write spent getting through the busy-retry loop, how many attempts it took, whether it ever really hit a locked database, how long it then held `BEGIN IMMEDIATE`, and which project, process and lock policy it belonged to. Writes that spend a hook's whole lock budget and fail open are recorded before the fail-open hook runs, since that hook can exit the process. `node <plugin>/lib/lock-trace.js [<file>] [--json]` summarises a collected trace per operation and per lock policy with p50, p95 and worst wait, worst hold, and the count that reported a locked database. Read that last count with the wait percentiles, not instead of them: a wait absorbed inside SQLite's own busy timeout is recorded as a wait but not as a block, so a multi-second worst wait can legitimately sit beside a zero block count. Nothing changes about lock behavior, timeouts, retry counts or the board schema, and with the variable unset tracing resolves nothing, opens nothing and writes nothing.
