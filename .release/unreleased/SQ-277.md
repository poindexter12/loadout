---
ref: SQ-277
title: "sidequest: a shared-tree submit no longer refuses a candidate over a sibling's uncommitted file or a sibling's commit"
bump: minor
plugins: [sidequest]
---

Two shared-tree submits were refused after their work had been committed correctly, and in both cases the refusal named something the executor had no legal way to act on (reported from nexia SQ-41 and SQ-42, 2026-10-07).

A `dirty_scope` refusal demanded the executor commit paths the `commit` tool deliberately refuses to take. An auto-approved test-scope widening turns one requested file into its enclosing test root, so a live sibling's uncommitted work inside that directory counted as uncommitted changes inside this ticket's declared scope. SQ-276 had already taught the commit side to leave those paths out; the submit gate still demanded them, which left the only ways forward being to sweep a sibling's work into the commit or to revert it. A shared-tree submit now drops from the dirty-scope surface the paths the board can prove are not this ticket's work, by the same attribution the commit uses: paths another live claim's execution scope covers, and paths whose dirty-baseline identity has not moved since the dispatch launched. They are reported, with their owning refs, through the shared-tree working-path advisory and recorded on the submission as `excludedScopePaths`, so nothing is silently dropped. The executor's own uncommitted work inside its own scope is still refused, an exactly-declared path is never excluded on a sibling's account, and an isolated worktree keeps the gate unchanged because one executor owns the whole checkout.

An `outside_scope` refusal counted a sibling's commit against the candidate. A shared-tree candidate's range ran from its dispatch base, so a sibling that committed first put its paths inside this candidate's range; the explicit `--base` remedy then refused that commit as an unrecognized base. No executor had a route until a sibling submitted, which is an ordering none of them can see or arrange, and sequential committers in one shared tree will always produce it. The commits the board's own `commit` tool authored for a sibling's held claim are now approved range boundaries alongside a sibling's submitted candidate, so the range starts after them instead of swallowing them. A boundary survives its sibling's release: the commit is still in the tree's history, and an executor that died after committing must not deadlock whoever committed behind it. The existing ancestry and nearest-base guards still decide which boundary a given candidate may start from.
