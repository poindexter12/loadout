---
ref: SQ-362
title: A ticket that records its own verifier keeps it under verifyKind suite, and dispatch now echoes the command it pinned
bump: patch
plugins: [sidequest]
---

A ticket could declare a targeted gate, declare `executorVerifyKind: "suite"` alongside it, and dispatch against the whole plugin suite instead. Dispatch resolved the project's named suite whenever the kind was `suite`, and a resolved suite outranks the recorded command, so the declared string became dead text. Nothing said so at filing time, at dispatch time, or in the briefing. The only way to see it was to read `dispatch.verificationRequirement` after the fact, which is not a thing anyone does on a ticket that already looks right: both fields were populated, mutually consistent, and correct on inspection.

The measured cost on SQ-324 was two Opus attempts, roughly two hours of wall clock and about 270k executor tokens, spent on `npm ci` plus the full suite in place of a gate that runs in under a minute. The first attempt exhausted its context inside the gate having recorded nothing on the board.

Dispatch was also the only surface that read the kind this way. The pending-submission re-pin, the briefing's legacy fallback, and the work route all pass a recorded command through under kind `suite`, and the `verifyKind` schema already promises that "command and suite execute a validated command". So a ticket that records a runnable verifier of its own now keeps it, whatever kind it declares, and dispatch agrees with everything else. The named suite stays the fallback for a ticket that records nothing runnable, which is still derived and still announced as derived.

Precedence alone would not have saved those two hours, because nothing was echoing the pinned command either way. Dispatch now appends a notice naming the command it actually pinned and where that command came from: the ticket's own `executorVerify`, a suite or gate the board derived, or an attestation with no command to run. It is appended last so it ranks below real defect warnings, and it reaches both the MCP dispatch result and the CLI, which is where a mismatch between what a ticket declares and what its executor will run becomes visible before the executor burns an hour on it.

One sibling case is deliberately untouched and still open: an empty `executorVerify` under `executorVerifyKind: "command"` also falls back to the named suite. That is a missing-command problem rather than a discarded-command one, it is caught by a different guard, and this change does not close it.
