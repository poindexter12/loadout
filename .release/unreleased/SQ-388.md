---
ref: SQ-388
title: The dispatch lock-scope test counts work under the write lock instead of timing it
bump: patch
plugins:
  - sidequest
---

The test that guards "no Git or filesystem work runs while the board write lock is held" no longer compares one wall-clock lock hold against one sampled `git rev-parse`. Both sides of that ratio were noisy samples, so a scheduler stall or GC pause inside a transaction failed it on CI (an 18.14ms hold against a 4.49ms spawn) with no Git work under the lock at all. A child process now instruments `child_process` and `fs` before the store loads, tracks the lock window by the only statements that take and drop it (`BEGIN IMMEDIATE`, then `COMMIT`/`ROLLBACK`), and counts every spawn and fs call made inside that window. The assertions are counts, not durations: zero subprocess spawns, zero directory enumerations, and zero fs calls on project working-tree paths under the lock, with positive controls that the lock was taken and that Git spawns and fs calls were seen outside it, so the zeros cannot be vacuous. The store's deliberate cheap re-validation under the lock (reading `.git/HEAD` and ref files directly rather than spawning `git rev-parse`, stat-ing the model catalog, realpath of the project root, renaming the dispatch token into place) stays allowed; a blanket "zero fs calls" would have failed correct code. No machine load changes a count.
