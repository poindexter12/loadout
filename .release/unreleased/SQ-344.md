---
ref: SQ-344
title: Recording an external delivery no longer blames the evidence when the target branch is held by a worktree whose directory is gone
bump: patch
plugins: [sidequest]
---

When the canonical project root is not on a ticket's target branch, `recordDeliveredSubmission`
looks for the one linked worktree that could have it checked out and reads the branch from
there instead. That lookup walked `git worktree list --porcelain` line by line and answered as
soon as it saw a matching `branch` line — but git prints `prunable` and `locked` *after* the
branch, so a record could never be judged whole before the walk had already returned its path.

A worktree directory deleted without `git worktree remove` still holds its branch in git's
administrative records. The lookup handed that dead path back, the caller adopted it as the
repository to read, and the very next `git rev-parse` was spawned into a cwd that no longer
exists. The ENOENT surfaced as `delivery_evidence_unavailable` — a refusal that blames the
delivery evidence for a stale worktree registration, and points whoever reads it at the commit
rather than at the leaked directory that actually caused it.

The lookup now parses whole porcelain records and skips any whose worktree git reports as
`prunable` or `locked`. Locking matters on its own: it suppresses the prunable line entirely,
so a locked worktree that is equally gone is only ever reported as `locked`. Falling through to
no worktree leaves the caller on the registered checkout, where a target branch that really did
merge is still accepted by its ancestry, and one that did not earns the accurate
`branch_not_checked_out`. A live worktree holding the branch is read exactly as before.

`parseWorktreeList`, the shared porcelain parser the sweep and warning paths already use, gained
the `prunable` flag in the same change and now records both flags by presence rather than by
their reason text, which git leaves optional and sometimes empty.
