---
ref: SQ-273
title: Concurrent prepares of one ticket serialise on its file lock again, without holding the global write lock
bump: patch
plugins:
  - sidequest
---

The per-ticket file lock and the machine-global board transaction are now separate primitives (`withTicketFileLock`, `withTicketLocks`; `withTicketLock` keeps its exact contract). `prepareDispatch` holds the ticket's file lock across its whole plan-then-commit sequence and enters the transaction only for the short recheck-and-store, so a second prepare of the same ticket waits instead of planning alongside the first and running the worktree reclaim twice. The global write lock hold is unchanged from SQ-268. The lock order is documented and enforced: ticket file locks before the transaction, never inside it (`SIDEQUEST_LOCK_ORDER`). The two dispatch paths that nested one ticket lock inside another's transaction now take both locks together, sorted, before the transaction.
