---
ref: SQ-455
title: "Briefing token refusals now say whether the token file was missing, unreadable, invalid, or from a superseded dispatch"
bump: patch
plugins: [sidequest]
---
`sidequest briefing --token-file` used to print one line, "dispatch token was refused or its token file was unavailable", for every token failure, so an executor could not tell whether to retry or ask for a redispatch. `readDispatchBriefing` now keeps the token-file read outcome and refuses with a distinct reason and message for each case: `token_file_missing`, `token_file_unreadable` (retry once read access is restored, no redispatch), `token_file_invalid` (empty or multi-line file), `token_mismatch` (a valid token that is not the current dispatch's), and `no_dispatch`. When the token file is not the current dispatch's own file, the message says a later dispatch superseded the launch and tells it to stop and report to the orchestrator instead of asking for another dispatch. Stale-dispatch and unknown-ticket refusals are unchanged.
