---
ref: SQ-71
title: "sidequest: the unset-environment-variable refusal no longer recommends a default value the validator cannot choose"
bump: patch
plugins: [sidequest]
---

The refusal for a verify that reads an ambient environment variable told the author to "set a portable default such as `${NAME:-/tmp}`". `/tmp` is a value the validator picked while knowing nothing about what the check needs, so an author who followed the remedy got a verify that still ran, still exited 0 in plausible cases, and no longer checked what it claimed to. That is a worse outcome than the refusal: a rejection costs five minutes, a false green can go unnoticed indefinitely. The hazard is general — a default is reasonable advice for a path-shaped variable and actively wrong for anything else — and the validator has no way to tell which it is looking at.

The refusal now states the actual problem, that the check depends on whatever the operator's environment happens to hold, and names only remedies that keep the oracle intact: write the value the check needs into the command, bind the name in the command itself (`NAME=<value> && <command>`), or record it as `manual: <what you checked>`. A `${NAME:-<default>}` fallback is mentioned last and qualified, as only helping when that default still checks what the verify claims to check, rather than offered as a value to paste. Each of the three is accepted by the validator, so following the remedy cannot land the author back on a refusal. The `%NAME%` form carries the same framing without the shell-binding suggestion. The refusal itself is unchanged in scope: a genuinely ambient name is still refused, and still named.

This closes the remaining half of #19. The reported half, the validator reading a shell-bound loop variable as an environment reference, was fixed by SQ-202 in sidequest 5.4.0; its tests are what prove that half stays fixed.
