---
ref: SQ-158
title: groomClose manual delivery accepts a wave branch that has already merged
bump: patch
plugins:
  - sidequest
---

`groomClose` with `deliveryMethod: manual` and a `deliveryCommit` no longer refuses a ticket whose target is a wave branch (e.g. `sidequest/wave/<name>`) once that branch's PR has merged into the checked-out branch. Before this, the guard required the exact target branch to be currently checked out and refused with `branch_not_checked_out` even when the delivery was legitimately reachable from the now-current branch (typically `main`) — including the common case where the wave branch was deleted after merging. The guard now also accepts the delivery when the target branch, or the delivery commit itself, is an ancestor of HEAD, mirroring how SQ-99 accepts a reviewed descendant of the pinned candidate.

Separately, when the target branch is checked out in a linked worktree rather than the canonical project root, the guard now reads the branch from that worktree instead of reporting "currently on main" from the root it never left. A wave branch that is genuinely unmerged and not checked out anywhere is still refused with `branch_not_checked_out` as before.

This fix applies to `recordDeliveredSubmission` only, which backs `groomClose`'s manual/external delivery path. The wave-delivery and integration guards (`integrateAssembledWave`, `integrateSubmissionUnlocked`) require the target branch to be genuinely checked out because they actively write new commits onto it (merge or cherry-pick candidates); they have no "already delivered externally" acceptance path and were left unchanged.
