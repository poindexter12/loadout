---
ref: SQ-162
title: Pinned verify-capture runs in and records the executor's isolated worktree, and refuses a capture it cannot bind to the candidate
bump: patch
plugins: [sidequest]
---

A pinned verify-capture for a ticket with a live isolated dispatch now runs in that dispatch's worktree, whatever directory the wrapper is started from, and records the worktree's HEAD as the candidate. Before, it ran in the caller's directory and recorded that directory's HEAD. An executor whose shell stood in the shared checkout captured main's commit, and submit then refused the green candidate because no capture matched it (SQ-81).

The wrapper now refuses up front, before running anything and without recording a capture, when it cannot bind the run to the candidate. These cases each name the reason:
- The dispatch has no bound worktree.
- The worktree is gone or is not its own checkout (`capture_worktree_unavailable`).
- The worktree has uncommitted or untracked changes (`capture_candidate_uncommitted`), because the recorded commit would not be the code that ran (SQ-158).

A capture whose worktree HEAD moves while the command runs is not recorded (`capture_candidate_moved`).

Shared-tree, working-tree-delivery, and finished or undispatched tickets capture exactly as before. Isolated executor briefings now say that the wrapper binds the worktree and must run after the board commit.
