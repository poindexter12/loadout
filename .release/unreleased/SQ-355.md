---
ref: SQ-355
title: Emit MCP progress from `integrate` while a verify gate runs
bump: minor
plugins:
  - sidequest
---

`integrate` now emits a `notifications/progress` update when each pinned verify gate starts and
finishes, naming the phase (`candidate`, `merged-tree`) and, on exit, the status the gate returned
and how long it took.

A delivery runs the pinned verifier twice, once on the candidate and once on the merged tree, and
emitted nothing between them. A client that measures idleness aborted the call as dead: integrating
SQ-354 reported `Task failed: ... sent no response or progress for 1800s` while the underlying
integrate had already merged the candidate and went on to flip the ticket to `done`. The obvious
recovery from that false failure is to run `integrate` again, which stacks a second writer behind a
live one and starts a third concurrent suite on the same machine, the documented condition for gates
going falsely red.

Progress reports phase transitions, not liveness, so an integrate that genuinely wedges inside one
gate still goes quiet and still times out. Emission is opt-in per the MCP spec: the server reports
only when the client supplies a `progressToken`, and a failed write to the transport never turns a
healthy tool call into a failure.
