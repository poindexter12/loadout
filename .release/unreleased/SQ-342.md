---
ref: SQ-342
title: The verify-command preflight refuses a node --test gate whose package cannot load the TypeScript files it names, or that drops the preloads its own test script carries
bump: patch
plugins: [sidequest]
---

A pinned `executorVerify` of the form `cd plugins/sidequest && node --test "test/foo.test.ts"` passed every check in `validateVerifyCommand` and then loaded zero tests on every machine. The package is `"type": "commonjs"`, so once Node has stripped the types it reads those files as CommonJS, where their `import` statements are a SyntaxError. Five tickets carried that form, two of them all the way to an executor, and the only thing that caught it was a human reading a 300ms `failed_suite` capture.

The bare form is also the one that omits `--import ./test/_sidequest-test-home.ts`, the preload that points `SIDEQUEST_HOME` at a sandbox. Had the gate loaded, the sidequest suite would have created fixture projects and tickets in the operator's real board, the same class of accident as a test suite clobbering a real `settings.json`.

The preflight already read the target package's manifest to check `npm run <script>`, so both failures are decidable where it stands. A `node --test` gate is now refused when the files it names are TypeScript, it carries no type-stripping loader, and the nearest `package.json` is not `"type": "module"`; and when it omits an `--import` preload that the package's own `--test` script loads. Each refusal names the package's `test:files`-style script and the ready-made `npm run <script> -- <files>` form rather than leaving an author to infer a rewrite.

One narrower gap closed with it: the operands are now read from the whole invocation rather than only from what follows a literal `node --test`, so a command that puts its loader and preloads ahead of `--test` is parsed instead of ignored. The existing `matches no files` refusal picks that up too, having previously seen no operands at all in a loader-carrying command.

The `matches no files` and missing-directory refusals stay behind the `cd` guard they have always had, now with the reason recorded next to it: without a `cd` the base is the repository root, which always exists, and a root-relative operand naming a file the ticket has yet to create is greenfield work that the path warning reports rather than refuses. The new runner check needs neither assumption, because it resolves the package from the files the operands actually match, so it runs with or without a `cd`.
