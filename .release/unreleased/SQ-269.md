---
ref: SQ-269
title: Lock-trace records name the board function that held the write lock
bump: patch
plugins: [sidequest]
---

SQ-262's lock trace recorded the label of the statement being run, and almost every board write arrives at that seam as `writing transaction`. A collected trace could say how long the board waited but not which operation was holding the lock, which is the half that matters when deciding whether a slow write needs shrinking or the shared database needs splitting. Each wait and hold record now also names its caller, resolved from a bounded stack walk at the seam rather than from anything passed in at a call site, and carries the few frames it was resolved from so the choice can be checked by eye. The name is the outermost board function involved, so a wait taken deep inside `releaseTicket` reports `releaseTicket`, and the statements nested inside a transaction inherit the name of the frame that actually holds the lock instead of claiming the wait as their own. `node <plugin>/lib/lock-trace.js` now leads with a per-caller breakdown — waits, how many of them were nested, p50, p95 and worst wait, and worst hold — alongside the existing per-operation and per-policy tables, and the trace report also shows nested counts per row. A trace collected before this change still summarises, with its records grouped as unattributed. Lock behavior, timeouts, retry counts and the board schema are unchanged, and with `SIDEQUEST_LOCK_TRACE` unset there is still no stack walk, no allocation and no file written.
