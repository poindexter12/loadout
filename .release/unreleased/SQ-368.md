---
ref: SQ-368
title: A board server whose session started in a since-deleted directory recovers instead of failing dispatch with ENOENT
bump: patch
plugins: [sidequest]
---

The board MCP server inherits the Claude Code session's working directory. When that directory is later removed, which Sidequest's own worktree sweeps can do, every `process.cwd()` in the server throws ENOENT for the rest of the process's life. Read-only tools such as `pulse` kept working, so the board looked healthy until `dispatch`, which reads the cwd unconditionally, failed with a bare `process.cwd failed` error. `/reload-plugins` and `claude --continue` restart the server into the same dead path, so the only remedy was exiting Claude Code entirely.

The server now probes its working directory at startup and again before each request, because the directory can also vanish while a long-lived server is running. When it is gone, the server moves to `CLAUDE_PROJECT_DIR` if that still exists, otherwise the home directory, and writes one stderr line naming the deleted directory and where it continued from. The CLI `dispatch` command runs the same guard. If no surviving directory can be entered, the message says so and names the actual remedy: a fresh Claude Code process from a checkout that exists.

Scope is the server entrypoint and the dispatch path. Other `process.cwd()` call sites are protected inside the MCP server by the per-request guard, but CLI commands other than `dispatch` are not yet guarded.
